# 从源码到可运行实验

读懂一个大型运行时，不等于记住它的目录结构。更有效的起点是选一个会失败的小问题，把失败原因变成可检查的规则，再实现维持这条规则的最小机制。本课的八个阶段沿着这种因果关系排列，而不是逐文件翻译 DeepSeek Harness。

## 先找到系统必须守住的事实

以工具执行为例，先问三个问题：模型提出调用以后，谁决定能不能执行？工具乱序完成时，谁决定结果进入历史的顺序？收到取消时，已经开始的调用会留下什么事实？

这些问题分别落到执行前决策、有序结算、恢复分类。上游工具管线、批次执行器和会话恢复代码提供了具体答案，而不是仅凭一个“工具调用”名词推测行为。

[并发池与独占屏障](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/core/tools/src/batch.ts#L50-L279)

把源码读成下面这张卡片，再开始写实验：

| 字段 | S05 的例子 |
|---|---|
| 失败现象 | 第二个工具先完成，历史顺序被改变 |
| 必须成立的不变量 | 结果按模型声明的调用顺序提交 |
| 最小输入 | 两个可并发工具，第二个更快 |
| 可观察证据 | 完成事件顺序不同，但模型历史中的结果顺序稳定 |
| 保留的机制 | 有界并发、独占屏障、顺序结算 |
| 暂时移除的复杂性 | 流式 UI、远程调用、持久化、供应商协议 |
| 真实实现差异 | 教学版按有限波次执行；上游采用滚动并发池 |

## 一次只增加一个核心机制

S01 只回答“工具结果怎么回到模型”。S02 把事实日志和模型视图分开，才有基础讨论后面的恢复、压缩和 fork。S03 给注册项明确的所有者，S04 才能把可见工具与执行权限区分开。顺序来自机制依赖，不来自生产仓库中文件出现的顺序。

每个阶段是一份可独立运行的累计快照。读者可以同时运行相邻两课，查看 delta.patch，然后解释新增代码修复了哪个失败。可运行不代表真实模型调用：ScriptedModel 故意返回确定的响应，让我们把模型质量与运行时正确性分开。

## 从反例开始，最后回到源码

1. 运行基线，写下预期事件和最终状态。
2. 改坏一个条件，例如让 ask 在缺审批通道时默认通过。
3. 让测试证明错误存在：工具体不该执行，却执行了。
4. 增加最小修复，再测试拒绝、异常和取消分支。
5. 阅读固定 commit 的源码锚点，指出教学版保留和省略的行为。

例如 S04 的关键不是“多了一个 if”，而是执行权被明确放在模型之外。没有审批通道时返回拒绝，审批允许后仍须经过 guard，策略异常也不能放行。每条边界都应该能被一个独立反例推翻，也能被测试保护。

## 轨迹是实验输出，不是配图中的想象

轨迹实验室的数据由 scripts/build_traces.py 调用教学运行时实际执行后生成；各课的 walkthroughs/ 则保留本课机制的独立走读。网页逐步展示事件、日志长度和模型历史；Markdown 保留同一批运行的静态表格。交互控件只是读取记录，不在浏览器连接模型或运行远程工具。

先预测再揭晓比直接看最终答案更有用：tool/call 能否证明成功？不能。日志增加一条，模型消息是否一定增加？也不能。surface 替换为何不删除旧事实？这些判断共同组成你对系统的可检验理解。

## 固定版本，保留诚实的简化

sources.json 为每个锚点记录完整 commit、路径、行范围、定位符和文件 SHA-256。reference/upstream 包含对应 MIT 源文件，离线也能核对。更新上游时先重新核对契约，再修改实验、测试和讲义；不能只替换 URL 中的版本号。

我们刻意没有实现供应商流协议、操作系统沙箱、完整持久化和插件生态。纯内存工具、固定响应、人工摘要让课堂实验足够小，但不证明真实模型、权限系统或生产性能。每课的“与真实实现的差异”是课程的一部分，而不是应被隐藏的不足。

## 如何贡献一课

新增机制时，先提交一个能稳定重现旧行为不足的测试，再补最小实现、独立快照、讲义和源码锚点。讲义采用“失败 → 规则 → 实现 → 运行观察 → 练习 → 源码核对”的结构。

内容只在 Markdown 中维护；book.json 管理顺序，代码册和轨迹表格从实际代码生成，Pandoc 负责网页转换。构建检查防止失效链接、重复锚点和源码锁漂移。把可重现的证据放进课程，比增加更多框架依赖更重要。
